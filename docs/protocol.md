# 통신 규약 (MQTT 토픽 · 페이로드)

더미 서버(발행자)와 트윈(구독자)이 지키는 데이터 계약입니다.
코드 정의는 `src/Shared`에 있으며, 이 문서와 코드가 다르면 코드를 기준으로 하고 문서를 고칩니다.

## 1. 기본 원칙

- **서버는 원시 신호만 보낸다.** "잼 발생" 같은 판단은 보내지 않는다. 판단은 트윈의 몫이다.
- **트윈은 데이터를 믿고 따라가되 맹신하지 않는다.** 순서, 중복, 이상값, 끊김을 스스로 검증한다.
- 브로커는 더미 서버 프로세스에 내장한다. 기본 주소 `127.0.0.1:1883`.

## 2. 토픽 구조

형식: `dt/{deviceId}/{category}/{signal}` (기본 deviceId = `conveyor01`)

| 토픽 | 내용 | 메시지 타입 | 주기 | QoS | Retained |
| --- | --- | --- | --- | --- | --- |
| `dt/conveyor01/status` | 연결 상태 (Last Will 대상) | StatusMessage | 변경 시 | 1 | O |
| `dt/conveyor01/state/run` | 가동 상태 | RunStateMessage | 변경 시 | 1 | O |
| `dt/conveyor01/telemetry/belt_speed` | 벨트 속도 (m/s) | TelemetryMessage | 500ms | 0 | O |
| `dt/conveyor01/telemetry/motor_temp` | 모터 온도 (degC) | TelemetryMessage | 1000ms | 0 | O |
| `dt/conveyor01/telemetry/motor_current` | 모터 전류 (A) | TelemetryMessage | 500ms | 0 | O |
| `dt/conveyor01/telemetry/load_weight` | 입구 로드셀 무게 (kg) | TelemetryMessage | 물건 통과 시 | 1 | X |
| `dt/conveyor01/sensor/entry` | 입구 광전 센서 엣지 | SensorEdgeMessage | 엣지 발생 시 | 1 | X |
| `dt/conveyor01/sensor/exit` | 출구 광전 센서 엣지 | SensorEdgeMessage | 엣지 발생 시 | 1 | X |

트윈 구독: `dt/conveyor01/#`

### QoS · Retained 선택 이유

- **주기 측정값은 QoS 0 + Retained.** 곧 다음 값이 오므로 하나쯤 잃어도 되고, 재접속 시 마지막 값으로 즉시 화면을 복원한다.
- **상태·이벤트는 QoS 1.** 가동 상태 변화와 센서 엣지는 하나라도 놓치면 물건 추적과 잼 판단이 틀어진다. 중복 수신 가능성은 seq로 걸러낸다.
- **센서 엣지는 Retained 하지 않는다.** 과거 엣지가 재접속 시 다시 오면 물건이 하나 더 생긴 것처럼 보이기 때문이다.

## 3. 페이로드

JSON, 필드명 camelCase, enum은 소문자 문자열.

### 공통 헤더 (Envelope)

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| `sid` | string | 발행자 세션 ID. 서버를 재시작하면 바뀐다 |
| `seq` | long | 토픽별 순번. 세션 내에서 1부터 1씩 증가 |
| `ts` | long | 발행 시각, Unix epoch 밀리초 |

### TelemetryMessage

```json
{ "sid": "a1b2c3", "seq": 1024, "ts": 1792886400123, "value": 0.50, "unit": "m/s", "quality": "good" }
```

`quality`: `good` | `uncertain` | `bad` (센서 자체가 판단한 신뢰도. OPC UA Quality 개념의 단순화)

### SensorEdgeMessage

```json
{ "sid": "a1b2c3", "seq": 57, "ts": 1792886400456, "blocked": true }
```

`blocked: true` = 물체가 빛을 가리기 시작(감지), `false` = 물체가 빠져나감.
광전 센서는 물건의 ID를 모른다. 트윈은 입구·출구 엣지의 **순서(FIFO)** 로 물건을 추적한다.

**2단계부터 출구에 스토퍼가 있다.** 앞단이 출구 센서에 닿은 물건은 그 자리에 멈춰 로봇을 기다리고,
출구 `false`는 물건이 벨트 끝을 지나갈 때가 아니라 **로봇이 집어 들 때** 온다 (같은 순간 로봇의 `DI_VacuumOk`가 켜진다, [robot-opcua.md](robot-opcua.md)).
메시지 형식은 그대로이고 의미만 "센서 앞에서 물건이 사라짐"으로 같다. 로봇이 늦으면 뒤 물건이 출구 앞에 쌓여 출구 감지가 늦어지므로,
트윈은 출구가 막혀 있는 동안 뒤 물건의 잼 판단용 이동 거리를 쌓지 않는다 (`ItemTracker.Tick`, 2단계 6일 차).

### RunStateMessage

```json
{ "sid": "a1b2c3", "seq": 3, "ts": 1792886400000, "state": "running", "reason": null }
```

`state`: `stopped` | `running` | `fault`

### StatusMessage

```json
{ "online": true, "sid": "a1b2c3", "ts": 1792886399000 }
```

서버는 접속할 때 `online: true`를 retained로 발행하고, 같은 토픽에 `online: false`를 Last Will로 등록한다.
정상 종료 때는 Will이 발행되지 않으므로 서버가 `online: false`를 직접 발행한 뒤 접속을 끊는다.

- Last Will 페이로드는 접속할 때 미리 만들어 두므로, Will로 온 `offline`의 `ts`는 **끊긴 시각이 아니라 접속 시각**이다. 트윈은 끊김 시각으로 수신 시각을 쓴다.
- `StatusMessage`에는 `seq`가 없다 (브로커가 대신 발행하는 Will과 형식을 맞추기 위해).

## 4. 트윈 쪽 수신 규칙

| 규칙 | 내용 |
| --- | --- |
| 세션 전환 | `status`의 `sid`가 바뀌면 모든 토픽의 seq 기록을 초기화한다 |
| 과거·중복 폐기 | 같은 sid에서 `seq <= 마지막 처리 seq`면 버린다 |
| 엣지 유실 감지 | 센서 엣지의 `seq`가 건너뛰면 엣지를 잃은 것이므로 FIFO 짝이 어긋난다. 경고 후 물건 추적을 재동기화한다 |
| 출구 짝 검증 | 출구 감지는 FIFO 맨 앞 물건이 입구 이후 벨트 길이의 75% 이상 이동했을 때만 그 물건과 짝짓는다. 아니면 트윈이 보지 못한 물건(재동기화 전부터 벨트 위에 있던 물건)으로 센다 |
| 재생 시계 | 화면은 서버 시각(`ts`)을 따라가는 재생 시계로 움직인다. 목표 = 현재 시각 - 기준 지연 - 300ms이며, 기준 지연은 최근 1.5초 `수신 시각 - ts`의 최솟값이다 (메시지별 지터에 흔들리지 않음). 재생 시각은 순간이동하지 않고 배속(0~3배)을 조절해 목표를 따라간다. 데이터가 끊기면 최신 `ts` + 1초에서 멈춰 기다리고, 늦은 데이터가 오면 그 구간을 이어서 재생한다 |
| 순서 정렬 | 이벤트(센서 엣지, 무게)는 재생 시각이 그 `ts`에 도달할 때 `ts` 순으로 처리한다. 재생 지연 300ms가 곧 재정렬 버퍼다 (서버의 순서 뒤섞기 최대 250ms보다 커야 함). 같은 `ts`면 입구 → 무게 → 출구 |
| 이상값 판정 | `SignalSpec`의 유효 범위를 벗어나거나 `quality`가 `bad`면 표시값에 반영하지 않고 경고를 띄운다 |
| 끊김(stale) 판정 | 주기 신호가 주기의 3배 동안 오지 않으면 해당 값을 stale로 표시한다. 이상값으로 거부된 메시지도 "도착"은 한 것이므로 stale이 아니다 (통신 문제와 센서 문제를 구분해 알람 중복 방지) |
| 연결 끊김 | `status`에서 `online: false`를 받으면 전체를 오프라인 상태로 전환한다. 복구(`online: true`)되면 끊긴 동안의 엣지가 유실되었으므로 물건 추적을 재동기화한다 |
| 지연 측정 | 네트워크 지연 `수신 시각 - ts`와 화면 지연 `현재 시각 - 재생 시각`을 HMI에 표시한다 (같은 PC라 시계가 일치) |
| 잼 판단 | 입구 감지 이후 벨트가 움직인 거리(재생 시계 기준 속도 적분)가 `벨트 길이 × 1.5`를 넘었는데 출구 감지가 없으면 잼 (벨트 길이 = 1.95m, 6절). 속도가 일정하면 `벨트 길이 / 속도 × 1.5`초와 같고, 모터 정지·전송 지연 시간은 자동으로 빠진다 |

## 5. 장애 버튼과 기대 동작

| 서버 장애 버튼 | 서버가 하는 일 | 트윈의 기대 동작 |
| --- | --- | --- |
| 연결 끊김 | 소켓을 DISCONNECT 없이 닫음 → 브로커가 Last Will 발행. 현실(시뮬레이션)은 계속 진행 | 오프라인 표시, 재생 정지. 복구 후 retained로 상태 복원, 물건 추적 재동기화 |
| 전송 지연 | 모든 발행을 3초 지연 (`ts`는 생성 시각 유지). 순서를 지키는 송신 큐라서, 꺼도 밀린 메시지가 다 나간 뒤에 새 메시지가 나간다 (TCP 연결 하나에서는 뒤 메시지가 앞지르지 못함) | 지연이 시작되면 재생이 데이터 끝에서 기다리고, 늦은 데이터로 이어서 재생 (이동 거리 보존). 화면이 3초 늦다는 것을 HUD에 표시 |
| 순서 뒤섞기 | 발행마다 0~250ms 무작위 지연, 5%는 늦게 중복 재전송 | 재생 지연(300ms) 안에서 `ts` 순 처리, 중복·과거 `seq` 폐기 |
| 이상값 송신 | 온도 999.9(측정 범위 밖), 전류 `quality: bad` | 표시값 유지 + 이상값 경고 |
| 물건 걸림 | 벨트 중간 물건이 멈추고 뒤 물건이 쌓임 → 출구 엣지 없음, 모터 전류 +1.2A | 잼 판단, 해당 물건 하이라이트. 센서가 양 끝에만 있어 걸린 위치는 알 수 없다 |
| 모터 정지 | `state/run`을 `fault`로, 속도 0으로 발행 | 벨트 정지, 알람 발생, 잼 판단 보류 (벨트가 움직이지 않으므로) |

## 6. 설비 치수 (mk GUF-P 2000 CAD 실측)

| 항목 | 값 | 비고 |
| --- | --- | --- |
| 벨트 길이 | **1.95m** | 구동 드럼과 아이들 드럼의 중심 간 거리. 잼 판단 기준값. 코드: `Equipment.BeltLengthM` |
| 센서 위치 | 양쪽 드럼 축 위 | 입구 = 아이들 드럼(텐션 쪽), 출구 = 구동 드럼. 센서 간 거리 = 벨트 길이 |
| 벨트 폭 | 0.29m | |
| 드럼 지름 | 약 53mm | 벨트를 감은 외경 약 55mm |
| 벨트 윗면 높이 | 약 0.85m | 바닥 기준 |
| 반송 방향 | 아이들 드럼 → 구동 드럼 | 구동 드럼이 벨트 윗면을 당기는 일반 배치 |

예: 정상 속도 0.5m/s에서 잼 판단 시간 = 1.95 / 0.5 × 1.5 = 5.85초.
센서를 드럼 안쪽으로 옮기면 4절의 "벨트 길이"를 "센서 간 거리"로 바꾸고 이 표를 함께 고친다.

## 7. 정상 운전 기준값 (더미 서버 시뮬레이션)

| 신호 | 정상 범위 |
| --- | --- |
| 벨트 속도 | 0.5m/s ± 0.01 |
| 모터 전류 | 약 1.8A(무부하) ~ 2.5A, 벨트 위 하중에 비례 |
| 모터 온도 | 25°C에서 시작해 수 분에 걸쳐 약 47~50°C로 수렴 |
| 물건 | 0.3m 박스, 2~15kg, 6~8초 간격 (2단계: 로봇 사이클보다 길게. 1단계는 2.5~5초) |

모델 상세는 `src/DummyServer/README.md`. 트윈의 이상값 판정은 이 값이 아니라 `SignalSpec`의 센서 측정 가능 범위를 기준으로 한다.
